# 多视频批量抠图公平调度修复记录

日期：2026-07-27

状态：源码与隔离测试已完成，尚未部署到生产 Scheduler；当前生产任务继续由原 `1.3.4` 后端执行，没有重启或热替换任何服务。

## 1. 现场现象

同一个动画管家 API 客户同时提交两个序列帧抠图批次：

- `assetclaw:VID_BEA81E5CDA3E:matting:g1`，97 帧；
- `assetclaw:VID_49BB45CC93DB:matting:g1`，84 帧。

父批次均为 `RUNNING`，但三张 GPU 会在一段时间内全部执行同一个视频，另一个视频只有已物化的 `QUEUED` 子帧，Web UI 因此显示“尚未分配”。现场只读查询进一步确认，集群会整批切换到另一个视频，而不是让两个视频持续共享三张卡。

## 2. 根因

原调度器具备 API 客户级公平性，但动画管家的多个视频都属于同一个 `tenant_id`。进入同一租户后，原算法按照任务优先级老化和子帧创建时间选择，没有视频批次级公平维度。

结果是：

1. 等待较久的视频会因优先级老化持续胜出；
2. 三个 GPU 槽位可能全部分给同一个 `batch_id`；
3. 其他视频即使已有可运行子帧，也要等整组槽位切换后才开始；
4. Web UI 的“尚未分配”是后端真实状态，不是单纯的展示错误。

## 3. 新调度规则

保留原有生产客户优先、租户公平、显式优先级、心跳、节点兼容性、显存与并发限制。在同一个客户、同一种显式优先级的批量抠图任务内部，增加两级批次公平规则：

1. 当前活动子帧数量更少的视频优先；
2. 活动数量相同，最久没有获得 GPU 槽位的视频优先；
3. 两者仍相同，按批次最早子帧时间和 `batch_id` 稳定排序；
4. 选定视频后，才在该视频内部按老化优先级和帧顺序选择子任务。

预期行为：

- 3 张 GPU、至少 3 个可运行视频：前三个槽位分别给 3 个不同视频；
- 3 张 GPU、2 个可运行视频：先各得 1 个槽位，第三个槽位按轮转规则分配；
- 超过 3 个视频：新释放的槽位优先给当前没有活动帧的视频；
- 只有 1 个视频：仍可使用全部 3 张 GPU，不降低集群吞吐；
- 不同视频帧数不同不会影响公平性，短视频可以尽早完成，长视频继续使用释放出的容量。

## 4. 修改范围

- `packages/gpu_control_core/repository.py`
  - 在领取任务时读取候选批次最后领取时间；
  - 统计候选批次当前活动子帧数量；
  - 在租户内部按批次公平规则领取下一帧。
- `tests/unit/test_fairness.py`
  - 增加 84、97、121 帧三个不同规模视频争用三个槽位的验证；
  - 增加“没有活动帧的视频优先拿下一个空闲槽”的验证。

没有修改 ImageClip 工作流、节点、模型、参数、输出语义或动画管家接口。

## 5. 验证结果

- Python 源码语法检查通过；
- `git diff --check` 通过；
- 使用现有 API 运行镜像启动无网络、只读源码挂载的隔离测试容器；
- 公平调度测试全部通过；
- 84、97、121 帧三个视频的前三次选择结果分别为三个不同 `batch_id`；
- 当前没有活动帧的批次可以优先获得下一空闲槽。

## 6. 生产部署约束

当前生产仍有真实抠图子帧运行，因此本次只提交源码，不重启 Scheduler，不替换镜像，不修改数据库。

安全部署必须等到任务窗口允许后执行：

1. 确认全部节点 `current_jobs=0`，没有 ComfyUI 运行或等待队列；
2. 构建新的 GPU Control 版本镜像；
3. 只按既定滚动流程更新控制面；
4. 用 3 个不同帧数的真实测试视频确认三张卡分别获得不同批次；
5. 再开放动画管家生产流量，并观察批次进度、失败率和节点分配。
